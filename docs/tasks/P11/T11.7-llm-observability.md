# T11.7 LLM-observability, роутинг моделей, кэш

**Фаза:** P11 · **Слой:** backend, system-design · **Зависит от:** T9.1, T11.3 · **Размер:** M

> Короткая карточка. Подробное ТЗ пишется перед стартом фазы.

## Контекст
AI-фичи работают — теперь их нужно эксплуатировать: видеть каждый вызов в трейсе, знать стоимость по workspace, не платить дорогой моделью за простые запросы, переживать отказ провайдера и откатывать плохой промпт без деплоя.

## Observability
- Спаны по [OpenTelemetry GenAI semantic conventions](https://opentelemetry.io/docs/specs/semconv/gen-ai/): `gen_ai.system`, `gen_ai.request.model`, `gen_ai.usage.input_tokens / output_tokens`, `gen_ai.response.finish_reasons`; вложенные спаны на retrieval, rerank, каждый вызов инструмента (T11.5), каждый MCP-вызов (T11.6). Один трейс = путь «HTTP → retrieval → LLM → tool → batch в БД».
- Содержимое промптов и ответов в спанах — только при включённом флаге и с PII-скрабом (T11.4); по умолчанию — хэш и длина.
- Бэкенд трейсов: тот же, что в T9.1 (Grafana Tempo / Jaeger); опционально Logfire или Langfuse как специализированный UI — ADR, критерий: self-hosted и совместимость с OTel.
- Метрики (Prometheus): стоимость в USD по `workspace`, `feature`, `model`; TTFT (time to first token) и полная латентность p50 / p95; доля ответов из кэша; доля отказов guardrails; доля fallback-вызовов. Дашборд в репо; алерт на burn rate дневного бюджета.
- Выборка прод-трейсов с низкой оценкой пользователя («палец вниз») → экспорт в формат eval-набора (T11.4): прод кормит тесты.

## Роутинг и fallback
- Абстракция провайдера из T11.1 расширяется до «политики»: `cheap` для классификации / переформулировок / сводки истории, `strong` для ответа; выбор — по фиче и по сложности (простой классификатор или длина контекста).
- Fallback: при 5xx / таймауте / открытом breaker провайдера A — провайдер B с совместимой моделью; в трейсе видно, что был fallback; eval-набор прогоняется на обеих моделях.
- Опционально вместо своей реализации — [LiteLLM](https://docs.litellm.ai/) как gateway (роутинг, бюджеты, ключи); ADR «своя политика vs LiteLLM proxy».

## Кэш
- Exact cache: хэш (модель + промпт + параметры) → ответ, Redis с TTL; для детерминированных задач (суммаризация неизменённой страницы — ключ включает `content_hash`).
- Semantic cache для чата: embedding вопроса → поиск похожего (cosine > порога) в пределах **того же workspace и тех же прав**; ответ отдаётся как «похожий вопрос уже задавали» с возможностью спросить заново. Порог и TTL — параметры; метрика hit rate.
- Prompt caching провайдера (T11.1) — проверить, что префиксы стабильны и кэш реально срабатывает (видно в `cached_tokens`).

## Версии промптов и откат
- Промпты версионируются в коде (`prompts/<feature>_vN.py`) с changelog; активная версия выбирается вариантом feature flag (T9.5) по workspace / проценту.
- Процедура выката нового промпта в `docs/runbooks/prompt-rollout.md`: eval до → 5% → метрики (judge-score на выборке, доля «палец вниз», стоимость) → 100% или откат флагом без деплоя.

## Критерии приёмки
- [ ] Один трейс показывает путь «HTTP → retrieval → rerank → LLM → tool → batch», с токенами и стоимостью на каждом LLM-спане
- [ ] Провайдер A недоступен (тест с mock) → ответы идут через B, пользователь не видит ошибки, в метриках виден fallback
- [ ] Повторная суммаризация неизменённой страницы — из кэша, без вызова провайдера (тест)
- [ ] Semantic cache не отдаёт ответ пользователю без прав на исходные страницы (тест)
- [ ] Плохой промпт откатывается переключением флага; в трейсах видна версия промпта
- [ ] Дашборд стоимости по workspace в репо; алерт на 80% дневного бюджета срабатывает в тесте
