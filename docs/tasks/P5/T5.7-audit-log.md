# T5.7 Audit log на outbox-событиях

**Фаза:** P5 · **Слой:** backend, frontend, python · **Зависит от:** T5.4 · **Размер:** M

> Короткая карточка. Подробное ТЗ пишется перед стартом фазы.

## Контекст
В многопользовательском workspace вопрос «кто удалил страницу и когда» возникает в первую неделю. Outbox из T5.4 уже даёт поток доменных событий — audit log становится их первым «настоящим» потребителем, а не отдельной обвязкой в каждом сервисе.

## Backend
- Таблица `audit_log (id, workspace_id, actor_id, action, entity_type, entity_id, payload jsonb, request_id, ip, created_at)`; индексы по `(workspace_id, created_at desc)` и `(entity_type, entity_id)`.
- Наполняется consumer'ом outbox-событий: `page.created`, `page.deleted`, `page.restored`, `permission.changed`, `member.invited`, `member.removed`, `session.revoked`, `login.failed` и т.д. Без прямых `INSERT` из сервисов.
- Событие несёт `actor_id` и `request_id` (из `contextvars`, T0.5), чтобы запись в audit log связывалась с логами запроса.
- `payload` без секретов и без полного содержимого блоков — только diff метаданных; список допустимых полей на тип события.
- Retention по тарифу / настройке workspace (например, 90 дней), чистка cron-задачей из T5.3.
- Append-only: нет UPDATE / DELETE через приложение; отдельная роль БД для миграций.

## Frontend
- Страница «Активность» workspace: лента с фильтрами по пользователю, типу, периоду; keyset-пагинация из T2.5.

## Python-фокус
- Обобщённый consumer: `Protocol` для обработчика события, реестр `event_type → handler`, типизированные payload через discriminated union.

## Критерии приёмки
- [ ] Тест: удаление страницы → ровно одна запись в audit log с нужным `actor_id`, даже при повторной доставке события (идемпотентность по `event_id`)
- [ ] Тест: payload события `page.updated` не содержит текста блоков
- [ ] Записи audit log видят только `owner` / `admin` workspace
- [ ] По `request_id` из записи находятся логи запроса (T0.5)
