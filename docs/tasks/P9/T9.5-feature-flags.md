# T9.5 Feature flags и постепенный выкат

**Фаза:** P9 · **Слой:** backend, frontend, system-design · **Зависит от:** T5.1 · **Размер:** M

> Короткая карточка. Подробное ТЗ пишется перед стартом фазы. Можно брать раньше — сразу после P5.

## Контекст
Деплой и релиз — разные события. Фичу (и особенно новый промпт или модель в P11) нужно включать для 5% workspace, смотреть на метрики и откатывать одним переключателем без деплоя.

## Backend
- ADR: своя реализация vs [OpenFeature](https://openfeature.dev/) SDK с собственным провайдером vs внешний сервис (Unleash / Flagsmith self-hosted). Рекомендация для учебного проекта: своя модель данных + OpenFeature SDK как интерфейс, чтобы код приложения не зависел от реализации.
- Модель: `feature_flags (key, description, enabled, rollout_percent, rules jsonb, variants jsonb, updated_by, updated_at)`; правила таргетинга — по `workspace_id`, `user_id`, роли, окружению.
- Детерминированный bucketing: `hash(flag_key + workspace_id) % 100 < rollout_percent`, чтобы один workspace не «мигал» между включено / выключено.
- Кэш в Redis с pub/sub-инвалидацией (T5.1); при недоступности Redis — последнее известное значение, затем default из кода (fail-safe).
- `Depends(flag("new_editor"))` на уровне эндпоинта и `flags.is_enabled(...)` в сервисах; `variants` для A/B (например, `prompt_version: v1 | v2`).
- Каждая оценка флага попадает в контекст лога и трейса (T0.5, T9.1): `flags={"new_editor": true}` — иначе инцидент не разобрать.
- Админ-API и страница управления (только `owner`), изменения — в audit log (T5.7).
- Срок жизни флага: поле `expires_at`, напоминание в CI / логах про просроченные флаги — защита от «кладбища if'ов».

## Frontend
- Флаги для текущего пользователя отдаются одним запросом при загрузке; хук `useFlag("new_editor")`; SSR-совместимо (без мигания UI).

## Критерии приёмки
- [ ] Включение флага на 10% → ровно те же workspace попадают в 10% при каждом запросе (тест на детерминизм)
- [ ] Переключение флага применяется на всех инстансах API без рестарта, < 5 с
- [ ] Redis недоступен → приложение работает на последних известных значениях, флаг не «падает» в default мгновенно
- [ ] Просроченный флаг виден в отчёте (CI warning или `/admin/flags?stale=true`)
- [ ] В P11 версия промпта выбирается через вариант флага и откатывается без деплоя (проверяется в T11.7)

## Частые ошибки
| Антипаттерн | Почему плохо |
| ----------- | ------------ |
| `random() < percent` на каждый запрос | пользователь видит то старый, то новый UI |
| Флаг читается прямо из БД на каждый запрос | +1 запрос на каждый эндпоинт, БД становится точкой отказа для всего |
| Флаги никогда не удаляются | через год половина кода — мёртвые ветки |
