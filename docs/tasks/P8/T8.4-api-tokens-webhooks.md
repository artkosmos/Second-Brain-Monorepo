# T8.4 Публичный API: токены со scope и исходящие webhooks

**Фаза:** P8 · **Слой:** backend, frontend, system-design · **Зависит от:** T5.4, T4.2 · **Размер:** L

> Короткая карточка. Подробное ТЗ пишется перед стартом фазы.

## Контекст
Notion ценен интеграциями: Zapier, скрипты, боты. Для этого нужны два механизма — вход без cookie (API-токены) и выход без polling (webhooks). Это одна из самых частых продовых задач вообще и фундамент для MCP-сервера в T11.6: он будет авторизоваться теми же токенами.

## Backend: API-токены
- Персональные токены (`sb_pat_…`): показываются один раз, в БД — только хэш; префикс для поиска по утечкам (gitleaks-паттерн в T0.4).
- Scope: `pages:read`, `pages:write`, `databases:read`, `databases:write`, `webhooks:manage`; токен привязан к пользователю и workspace, права дополнительно ограничены правами пользователя (T4.2) — scope не расширяет, только сужает.
- `Authorization: Bearer` как альтернатива cookie в едином dependency `get_current_principal`; для Bearer CSRF не нужен, для cookie — нужен (T4.5).
- Срок действия, последнее использование, отзыв; rate limit отдельный на токен (T5.2).
- Версионирование публичного API: префикс `/api/v1`, политика deprecation в `docs/api.md`; `oasdiff` из T0.4 охраняет контракт.

## Backend: исходящие webhooks
- Подписка: `url`, набор событий (`page.created`, `page.updated`, `page.deleted`, `database.row.created`, …), секрет (показывается один раз).
- Источник событий — outbox (T5.4); доставка — задача в очереди (T5.3) с retry по экспоненте с jitter (например, 1 м → 5 м → 30 м → 2 ч → 12 ч), после исчерпания — DLQ и автоотключение подписки с уведомлением.
- Подпись `X-SB-Signature: t=<ts>,v1=<hmac_sha256(secret, ts + "." + body)>`, `X-SB-Event-Id` для идемпотентности на стороне получателя, `X-SB-Event-Type`; получателю отдаётся документ, как проверить подпись и защититься от replay (окно 5 минут).
- URL получателя проходит через SSRF-safe fetcher из T6.5; редиректы запрещены; таймаут 5 с; ответ 2xx — успех, всё остальное — retry.
- Порядок доставки не гарантируется, гарантируется at-least-once — это явно написано в документации.
- Журнал доставок (`webhook_deliveries`): статус, код ответа, длительность, число попыток; ручная повторная отправка.
- Описание событий — документ [AsyncAPI 3](https://www.asyncapi.com/) рядом с `openapi.json`; схемы payload генерируются из тех же Pydantic-моделей.

## Frontend
- Настройки workspace: «API-токены» (создать со scope, отозвать, последнее использование) и «Webhooks» (подписки, журнал доставок, кнопка «Отправить тестовое событие», «Повторить»).

## Python-фокус
- `hmac` / `hashlib`, constant-time сравнение; генерация AsyncAPI из Pydantic через `model_json_schema()`.

## Критерии приёмки
- [ ] Токен со scope `pages:read` не может создать страницу (403), токен пользователя-`viewer` с scope `pages:write` тоже не может
- [ ] Отозванный токен перестаёт работать немедленно (без ожидания TTL кэша или кэш инвалидируется)
- [ ] Тест с фейковым получателем: получатель недоступен 10 минут → после восстановления получает все события ровно один раз по `event_id`, подписи валидны
- [ ] Получатель, отвечающий 500 во всех попытках, попадает в DLQ; подписка отключена; запись в audit log (T5.7)
- [ ] Webhook на `http://10.0.0.1/` не создаётся (SSRF-проверка из T6.5)
- [ ] AsyncAPI-документ валиден (`asyncapi validate` в CI)

## Частые ошибки
| Антипаттерн | Почему плохо |
| ----------- | ------------ |
| Токен в БД в открытом виде | дамп БД = полный доступ ко всем workspace |
| Доставка webhook из HTTP-запроса пользователя | медленный получатель тормозит UI; падение получателя теряет событие |
| Подпись только тела, без timestamp | перехваченный запрос можно повторять бесконечно |
| Retry без jitter | тысячи подписок бьют в восстановившийся сервис одновременно |
