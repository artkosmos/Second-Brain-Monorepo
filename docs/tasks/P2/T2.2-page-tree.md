# T2.2 Дерево страниц

**Фаза:** P2 · **Слой:** backend, frontend · **Зависит от:** T2.1 · **Размер:** L

## Контекст
Заметки — плоский список. В Notion любая страница может лежать внутри другой страницы, на любой глубине; в сайдбаре — раскрывающееся дерево, сверху страницы — хлебные крошки.

## Цель
Сущность `pages` с вложенностью: создание внутри родителя, ленивая загрузка дерева, хлебные крошки, перенос поддерева с защитой от циклов.

## Модель данных

```
pages
  id            uuid PK            -- uuid, а не int: id видны в URL и не должны перебираться
  owner_id      FK users
  parent_id     uuid FK pages NULL -- NULL = корневая страница
  title         text NOT NULL DEFAULT ''
  icon          text NULL          -- emoji
  position      text NOT NULL      -- порядок среди соседей (fractional index, см. T2.3)
  created_at, updated_at
INDEX (owner_id, parent_id, position)
```

Миграция: `notes` → `pages`. Существующие заметки становятся корневыми страницами; `content` временно переезжает в поле страницы, в T2.3 — в первый блок `paragraph`. Миграция с данными, `downgrade` обратим.

## API

| Метод | Путь | Что делает |
| ----- | ---- | ---------- |
| `GET` | `/pages?parent_id=` | дети одного родителя (без `parent_id` — корни), с флагом `has_children` |
| `GET` | `/pages/{id}` | страница |
| `GET` | `/pages/{id}/breadcrumbs` | путь от корня до страницы |
| `POST` | `/pages` | создать `{title, parent_id?, after_id?}` |
| `PATCH` | `/pages/{id}` | title, icon |
| `POST` | `/pages/{id}/move` | `{parent_id, after_id?}` — перенос поддерева |
| `DELETE` | `/pages/{id}` | удалить с поддеревом (в T2.4 станет soft delete) |

`has_children` считается одним запросом (`EXISTS` или агрегат), не запросом на каждую страницу.

## Бизнес-правила
1. Хлебные крошки — один recursive CTE «вверх» от страницы:

```sql
WITH RECURSIVE path AS (
  SELECT id, parent_id, title, 0 AS depth FROM pages WHERE id = :id
  UNION ALL
  SELECT p.id, p.parent_id, p.title, path.depth + 1
  FROM pages p JOIN path ON p.id = path.parent_id
)
SELECT * FROM path ORDER BY depth DESC;
```

В SQLAlchemy — через `select(...).cte(recursive=True)`.

2. `move`: нельзя переместить страницу в саму себя или в своего потомка → `409 Conflict` (Problem Details, `type: .../page-move-cycle`). Проверка — CTE «вниз» от перемещаемой страницы или CTE «вверх» от нового родителя.
3. Родитель должен принадлежать тому же владельцу, иначе 404.
4. Лимит глубины (например 20) — защита от патологических данных и бесконечной рекурсии.
5. Все чтения и записи — только своих страниц (тест на IDOR: чужой `id` → 404).

## Frontend
- Сайдбар: корневые страницы; клик по стрелке — подгрузка детей (`useQuery(['pages', parentId])`), кэш по ключу родителя.
- «+» рядом со страницей — создать дочернюю, сразу перейти в неё с фокусом на заголовке.
- Drag-and-drop в дереве (dnd-kit): перенос внутрь и между соседями; optimistic update, откат при 409 с toast.
- Хлебные крошки над заголовком страницы.
- URL страницы: `/p/{id}`.
- a11y: `role="tree"` / `treeitem`, `aria-expanded`, стрелки ↑↓ — навигация, → / ← — раскрыть / свернуть, Enter — открыть.

## Python-фокус
- Recursive CTE в SQLAlchemy Core.
- Тип `uuid.UUID` в Pydantic и SQLAlchemy; генерация `uuid7` (сортируемые по времени).

## Критерии приёмки
- [ ] Миграция переносит существующие заметки без потерь, `downgrade` работает
- [ ] Перенос в себя или потомка → 409; тесты на оба случая
- [ ] Удаление родителя удаляет поддерево (тест на глубину 3+)
- [ ] Хлебные крошки — ровно один SQL-запрос (проверить счётчиком запросов в тесте или логом)
- [ ] Дерево в сайдбаре: lazy-load, создание, drag-and-drop, управление с клавиатуры
- [ ] Чужая страница во всех эндпоинтах → 404

## Частые ошибки
| Антипаттерн | Почему плохо |
| ----------- | ------------ |
| Грузить всё дерево целиком одним запросом | у пользователя с 5000 страниц сайдбар откроется за секунды |
| Рекурсия в Python с запросом на каждый уровень | N запросов вместо одного CTE |
| Проверка цикла только на фронте | API можно вызвать напрямую |
