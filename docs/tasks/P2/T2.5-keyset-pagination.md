# T2.5 Keyset-пагинация, фильтры, сортировки

**Фаза:** P2 · **Слой:** backend, frontend · **Зависит от:** T2.2 · **Размер:** M

## Контекст
`GET /notes` отдаёт всё сразу. При тысячах страниц это медленно и тяжело для фронта. `LIMIT/OFFSET` — не решение: `OFFSET 10000` заставляет БД прочитать и выбросить 10 000 строк, а вставка во время листания даёт дубли и пропуски.

## Цель
Список «Все страницы» с курсорной пагинацией, фильтрами и сортировкой; скорость не зависит от номера страницы.

## API
`GET /pages/all?limit=50&cursor=<opaque>&sort=-updated_at&q_title=...&created_from=...`

Ответ:
```json
{"items": [...], "next_cursor": "eyJ1IjoiMjAyNi0xMS0wNFQxMjowMDowMCIsImkiOiIuLi4ifQ", "has_more": true}
```

## Как работает keyset
Сортировка по `(updated_at DESC, id DESC)` — `id` разрывает ничьи. Курсор — base64 от последнего `(updated_at, id)`. Следующая страница:

```sql
WHERE (updated_at, id) < (:cursor_updated_at, :cursor_id)
ORDER BY updated_at DESC, id DESC
LIMIT :limit + 1           -- +1, чтобы узнать has_more без COUNT(*)
```

Индекс: `(owner_id, updated_at DESC, id DESC) WHERE deleted_at IS NULL`.

## Что сделать
1. Общий механизм пагинации в `core/pagination.py`: generic `Page[T]` (Pydantic generic model), кодирование / декодирование курсора, проверка подписи курсора или хотя бы валидация (битый курсор → 400, не 500).
2. Поддержать сортировки `updated_at`, `created_at`, `title` (для `title` — свой индекс; курсор знает, по какому полю сортировали; смена сортировки с чужим курсором → 400).
3. Фильтры: по подстроке заголовка (пока `ILIKE`, в P6 — FTS / trigram), по диапазону дат, «только корневые».
4. `limit` ограничен сверху (например 100).

## Frontend
- Страница «Все страницы»: таблица с сортировкой по клику на заголовок колонки.
- `useInfiniteQuery`, подгрузка при прокрутке (IntersectionObserver), «Загрузить ещё» как fallback.
- Фильтры и сортировка — в query string URL: ссылкой можно поделиться, кнопка «назад» работает.

## Python-фокус
- Pydantic generic models: `class Page(BaseModel, Generic[T])` и как это выглядит в OpenAPI.
- Сравнение кортежей (row values) в SQLAlchemy: `tuple_(a, b) < tuple_(x, y)`.

## Критерии приёмки
- [ ] `EXPLAIN ANALYZE` на 50k страниц: Index Scan, время первой и сотой страницы одинаковое
- [ ] Тест: вставка новой страницы во время листания не даёт дублей и пропусков (и тест, показывающий, что с OFFSET — даёт)
- [ ] Битый курсор → 400 Problem Details
- [ ] Фильтры и сортировка в URL; infinite scroll работает

## Частые ошибки
| Антипаттерн | Почему плохо |
| ----------- | ------------ |
| Сортировка только по `updated_at` | одинаковые значения → нестабильный порядок, дубли на границе страниц |
| `COUNT(*)` для `has_more` | полный подсчёт на каждый запрос |
| Курсор — голый `id` в query | клиент начинает его конструировать сам, контракт ломается при смене сортировки |
