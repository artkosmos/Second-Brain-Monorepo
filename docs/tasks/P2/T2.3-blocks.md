# T2.3 Блоки и fractional indexing

**Фаза:** P2 · **Слой:** backend, frontend · **Зависит от:** T2.2 · **Размер:** L

## Контекст
Сейчас содержимое — одна строка `content`. В Notion страница — это **упорядоченный список блоков** разных типов, каждый можно редактировать, перемещать и удалять отдельно.

## Цель
Страница состоит из типизированных блоков; порядок хранится так, что вставка между двумя блоками меняет одну строку в БД; редактор работает с клавиатуры.

## Модель данных

```
blocks
  id          uuid PK
  page_id     uuid FK pages ON DELETE CASCADE
  type        text NOT NULL       -- paragraph | heading | todo | code | divider
  content     jsonb NOT NULL      -- зависит от type
  position    text NOT NULL       -- fractional index
  created_at, updated_at
INDEX (page_id, position)
UNIQUE (page_id, position)
```

Содержимое по типам — Pydantic discriminated union:

```python
class Paragraph(BaseModel):
    type: Literal["paragraph"]
    text: str

class Heading(BaseModel):
    type: Literal["heading"]
    level: Literal[1, 2, 3]
    text: str

class Todo(BaseModel):
    type: Literal["todo"]
    text: str
    checked: bool = False

class Code(BaseModel):
    type: Literal["code"]
    language: str
    text: str

class Divider(BaseModel):
    type: Literal["divider"]

BlockContent = Annotated[
    Paragraph | Heading | Todo | Code | Divider,
    Field(discriminator="type"),
]
```

Миграция: `content` каждой страницы → один блок `paragraph`.

## Fractional indexing
Позиция — строка, которая сортируется лексикографически. Между `"a0"` и `"a1"` можно вставить `"a0V"`, между `"a0"` и `"a0V"` — `"a0G"` и т.д. Вставка, перемещение — меняется одна строка, соседи не трогаются.

1. Реализовать `generate_key_between(a: str | None, b: str | None) -> str` (алгоритм [rocicorp/fractional-indexing](https://github.com/rocicorp/fractional-indexing), base62) **сам**, в `core/ordering.py`, с тестами. Это хорошая алгоритмическая задача на Python.
2. Позицию вычисляет **сервер** по `after_id` / `before_id` от клиента, а не клиент присылает готовую строку.
3. `COLLATE "C"` у колонки `position`, иначе сортировка зависит от локали БД.
4. Та же функция используется для `pages.position` (порядок в дереве из T2.2).

## API

| Метод | Путь | Что делает |
| ----- | ---- | ---------- |
| `GET` | `/pages/{id}` | страница + все блоки по порядку, один-два запроса |
| `POST` | `/pages/{id}/blocks/batch` | список операций в **одной транзакции** |

Операции batch:

```json
{
  "ops": [
    {"op": "insert", "id": "<uuid от клиента>", "after_id": "...", "content": {"type": "paragraph", "text": ""}},
    {"op": "update", "id": "...", "content": {"type": "todo", "text": "купить", "checked": true}},
    {"op": "move",   "id": "...", "after_id": "..."},
    {"op": "delete", "id": "..."}
  ]
}
```

- `id` нового блока генерирует клиент (uuid) — фронт может сразу ссылаться на блок, не дожидаясь ответа.
- Одна невалидная операция → откат всего batch, 422 с индексом операции.
- Лимит операций в batch (например 200) и размера `content`.

## Frontend: блочный редактор
- Каждый блок — `contenteditable` или `textarea` (выбор в ADR; готовые редакторы вроде TipTap — пока **не** брать, в T7.4 будет осознанный выбор под CRDT).
- Enter — новый блок после текущего, фокус в него; Shift+Enter — перенос строки внутри блока.
- Backspace в пустом блоке — удалить, фокус в конец предыдущего.
- ↑ / ↓ на первой / последней строке — переход между блоками.
- `/` в пустом блоке — меню типов (фильтрация по вводу, стрелки, Enter).
- Markdown-шорткаты: `# ` → heading, `[] ` → todo, ```` ``` ```` → code, `---` → divider.
- Перетаскивание блоков за «ручку» (dnd-kit).
- Изменения копятся и отправляются batch-ом с debounce ~500 мс (полноценный автосейв с офлайном — T3.3).

## Python-фокус
- Discriminated unions в Pydantic: как выглядит ошибка валидации, как это отображается в OpenAPI и в сгенерированном TS-клиенте (union-типы на фронте).
- Алгоритм на строках: base62, сравнение, середина между ключами.

## Критерии приёмки
- [ ] `generate_key_between` покрыт тестами: начало, конец, между соседями, 1000 последовательных вставок в одно место — порядок верный, длина ключа растёт умеренно
- [ ] Batch атомарен: тест, где 3-я операция невалидна, — в БД ничего не поменялось
- [ ] Открытие страницы со 100 блоками — фиксированное число SQL-запросов (не N+1)
- [ ] Чужие блоки / блоки чужой страницы недоступны
- [ ] Редактор: все сочетания клавиш из списка выше работают; `/`-меню доступно с клавиатуры
- [ ] Миграция контента заметок в блоки обратима

## Частые ошибки
| Антипаттерн | Почему плохо |
| ----------- | ------------ |
| Целочисленный `position` с перенумерацией | вставка в начало = UPDATE всех блоков страницы |
| Клиент присылает готовый `position` | два клиента вставят одинаковый ключ; сервер не контролирует инвариант |
| `content` как `dict[str, Any]` без схемы | в JSONB окажется что угодно, фронт сломается на чужих данных |
| Один запрос на каждое нажатие клавиши | сотни запросов в минуту на одного пользователя |
