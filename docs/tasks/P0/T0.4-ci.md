# T0.4 CI на GitHub Actions

**Фаза:** P0 · **Слой:** infra · **Зависит от:** T0.2 · **Размер:** M

## Цель
Каждый PR автоматически проверяется линтером, типами, тестами и сборкой фронта; красный PR нельзя смержить.

## Что сделать
1. `.github/workflows/ci.yml`, запускается на `pull_request` и `push` в `main`.
2. Job `backend`: `astral-sh/setup-uv` с кэшем, `ruff check`, `ruff format --check`, `mypy`, `pytest` против `services: postgres` (тот же major, что на проде).
3. Job `frontend`: `actions/setup-node` с кэшем npm, `npm ci`, `npm run lint`, `npm run build`.
4. Фильтр путей (`paths` или `dorny/paths-filter`): правка только во фронте не гоняет бэкенд-тесты, и наоборот.
5. `concurrency` — отменять старый прогон при новом push в ту же ветку.
6. Включить required checks в защите `main`.
7. Job `security` (supply-chain): `pip-audit` (или `uv audit`) по lock-файлу бэкенда и `npm audit --audit-level=high` для фронта; `gitleaks` на диффе PR; Dependabot (или Renovate) для `uv.lock`, `package-lock.json` и GitHub Actions с группировкой minor / patch обновлений в один PR в неделю.
8. Job `api-contract` (после T0.6): [`oasdiff`](https://github.com/oasdiff/oasdiff) сравнивает `openapi.json` ветки с `main`; breaking change падает, если в описании PR нет метки `api-breaking`.

## Критерии приёмки
- [ ] PR с ошибкой линтера или теста нельзя смержить
- [ ] Полный прогон < 5 минут
- [ ] Бэкенд-тесты в CI идут на реальном Postgres, не на SQLite
- [ ] Тест: коммит с подложенным секретом (fake AWS key) блокируется `gitleaks`
- [ ] Тест: удаление поля из response-схемы без метки `api-breaking` роняет job `api-contract`

## Частые ошибки
| Антипаттерн | Почему плохо |
| ----------- | ------------ |
| Секреты prod в CI для тестов | тестам нужна только своя одноразовая БД |
| Тесты зависят от порядка запуска | в CI всплывает то, что локально «везло» |
| `pip-audit` только предупреждает, не падает | уязвимость с CVE живёт в проде месяцами |
| Dependabot без группировки | 20 PR в неделю, которые никто не читает |
