# T0.5 Логи, request-id, Problem Details

**Фаза:** P0 · **Слой:** backend, system-design · **Зависит от:** T0.3 · **Размер:** M

## Контекст
На проде без структурных логов и корреляции запросов разбор инцидента — гадание. Ошибки API сейчас в самописном формате.

## Цель
Каждый запрос оставляет в логах цепочку строк с одним `request_id`; все ошибки API — в стандартном формате RFC 9457.

## Что сделать
1. [structlog](https://www.structlog.org/): JSON в `staging` / `prod`, читаемый цветной вывод в `local`.
2. Middleware: берёт `X-Request-ID` из запроса или генерирует UUID; кладёт в `contextvars`; возвращает в заголовке ответа. Каждая строка лога содержит `request_id`, `method`, `path`, `status`, `duration_ms`, `user_id` (если есть).
3. Access-лог одной строкой на запрос; uvicorn access-лог отключить, чтобы не дублировать.
4. Ошибки в формате [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457): `type`, `title`, `status`, `detail`, `instance`, плюс `request_id` и `errors[]` для 422.
5. Необработанное исключение → 500 без стектрейса в ответе, со стектрейсом в логе.
6. Фронт: общий парсер Problem Details, toast показывает `title` / `detail`, `request_id` можно скопировать.
7. Никогда не логировать пароли, токены и cookie (processor для маскирования).

## Python-фокус
- `contextvars.ContextVar` и почему не `threading.local` в asyncio.
- Pure ASGI middleware vs `BaseHTTPMiddleware` (стриминг, производительность).

## Критерии приёмки
- [ ] Любой ответ, включая 500, содержит `X-Request-ID`
- [ ] По `request_id` из toast находится вся цепочка логов запроса
- [ ] Все ошибки API — `application/problem+json`; тесты проверяют формат 404 / 409 / 422 / 500
- [ ] Тест: пароль из тела `/auth/login` не попадает в лог
