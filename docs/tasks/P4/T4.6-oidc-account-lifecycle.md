# T4.6 OIDC-логин, верификация email, сброс пароля

**Фаза:** P4 · **Слой:** backend, frontend · **Зависит от:** T4.4, T4.5 · **Размер:** M

> Короткая карточка. Подробное ТЗ пишется перед стартом фазы.

## Контекст
Пароль + email — только один из способов входа. В 2026 году «войти через Google / GitHub» ожидается по умолчанию, а верификация email и сброс пароля есть в каждом реальном приложении. Это самые частые продовые кейсы auth, которых нет в уроках 18–19.

## Backend
- OIDC через [Authlib](https://docs.authlib.org/): Google и GitHub, Authorization Code + PKCE, `state` и `nonce` в server-side сессии.
- Проверка подписи `id_token` по JWKS провайдера; из claims берутся только `sub`, `email`, `email_verified`.
- Таблица `identities (user_id, provider, provider_sub)`; OAuth access token провайдера **не** становится сессией — после идентификации выдаётся своя пара access + refresh из T4.5.
- Связывание аккаунтов: если email уже есть и `email_verified = true` у провайдера — привязка к существующему пользователю; иначе — отдельный аккаунт и явное подтверждение через письмо.
- Верификация email при регистрации паролем: одноразовый токен (хэш в БД, TTL), письмо через очередь из T4.4 / T5.3. Неверифицированный пользователь ограничен (например, нельзя приглашать).
- Сброс пароля: `POST /auth/password/forgot` всегда отвечает 202 (не раскрывает, есть ли email); токен одноразовый, TTL 30 мин, после использования отзываются все refresh-токены пользователя.
- Rate limit на все три потока.

## Frontend
- Кнопки провайдеров на login / register, страница «подтвердите email», формы forgot / reset, раздел «Связанные аккаунты» в настройках.

## Python-фокус
- Проверка JWT по JWKS с кэшем ключей и ротацией; `secrets.token_urlsafe` и сравнение через `hmac.compare_digest`.

## Критерии приёмки
- [ ] Тест: `id_token` с неверной подписью или чужим `aud` → 401, пользователь не создаётся
- [ ] Тест: нельзя привязать провайдера с чужим неверифицированным email к существующему аккаунту
- [ ] Тест: токен сброса пароля одноразовый; повторное использование → ошибка; после сброса старые refresh-токены не работают
- [ ] `POST /auth/password/forgot` для несуществующего email отвечает так же, как для существующего (статус, время ответа в пределах шума)
- [ ] CSRF-защита из T4.5 покрывает callback OIDC (`state` проверяется)

## Частые ошибки
| Антипаттерн | Почему плохо |
| ----------- | ------------ |
| OAuth access token провайдера как своя сессия | срок жизни и отзыв не под контролем; смешаны identity и authorization |
| Автопривязка по email без `email_verified` | захват аккаунта через провайдера, где email не проверяется |
| Токен сброса в открытом виде в БД | утечка дампа = сброс любого пароля |
