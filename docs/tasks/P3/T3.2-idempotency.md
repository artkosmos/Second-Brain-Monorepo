# T3.2 Idempotency-Key

**Фаза:** P3 · **Слой:** backend, system-design · **Зависит от:** T2.3 · **Размер:** M

## Контекст
Пользователь нажал «Создать страницу», сеть подвисла, клиент повторил запрос по таймауту. Первый запрос на самом деле дошёл — теперь две одинаковые страницы. `PUT` и `DELETE` идемпотентны по природе, `POST` — нет.

## Цель
Любой `POST` с заголовком `Idempotency-Key` можно безопасно повторять: результат применяется ровно один раз, повтор получает тот же ответ.

## Модель данных
```
idempotency_keys
  key            text
  user_id        FK users
  request_hash   text          -- sha256 от метода + пути + тела
  status         text          -- processing | completed
  response_code  int NULL
  response_body  jsonb NULL
  created_at     timestamptz
PRIMARY KEY (user_id, key)
```

## Алгоритм
1. Ключа в заголовке нет → обычная обработка (для критичных эндпоинтов можно сделать ключ обязательным — 428).
2. `INSERT ... ON CONFLICT DO NOTHING RETURNING` со статусом `processing` — атомарно «захватить» ключ.
3. Захватили → выполнить операцию **в той же транзакции**, что и запись ответа: сохранить `response_code` / `response_body`, статус `completed`, commit.
4. Не захватили (ключ уже есть):
   - `request_hash` другой → `422` («ключ использован для другого запроса»);
   - `processing` → `409` + `Retry-After: 1` (параллельный дубль ещё выполняется);
   - `completed` → вернуть сохранённый ответ + заголовок `Idempotent-Replayed: true`.
5. TTL ключей — 24 ч; очистка периодической командой (в P5 — cron в очереди).
6. Реализация — переиспользуемая зависимость или декоратор для эндпоинта, а не копипаст в каждом роуте.

Подумай и опиши в PR: что делать, если процесс упал между шагами 2 и 3 (ключ навсегда `processing`)? Подсказка: `locked_until` / таймаут захвата.

## Где применить
`POST /pages`, `POST /pages/{id}/blocks/batch`, позже — загрузка файлов, экспорт, AI-запросы.

## Frontend
- Ключ (`crypto.randomUUID()`) генерируется на **намерение пользователя** (клик), а не на каждую попытку, и переиспользуется при ретраях.
- Ретраи мутаций в TanStack Query включены только для запросов с ключом.

## Python-фокус
- Декоратор или зависимость FastAPI, оборачивающая эндпоинт; хранение и воспроизведение ответа (`JSONResponse`).
- `hashlib.sha256` по канонизированному JSON (`json.dumps(..., sort_keys=True)`).

## Критерии приёмки
- [ ] Повтор с тем же ключом → тот же ответ, в БД одна страница
- [ ] Тот же ключ с другим телом → 422
- [ ] Два параллельных запроса с одним ключом → один выполнился, второй 409 (тест через `asyncio.gather`)
- [ ] Ошибка операции (например 422 валидации) — решение, сохранять ли её как результат, описано и покрыто тестом
- [ ] Ключи чужого пользователя не пересекаются с твоими
