# T3.5 Транзакции и уровни изоляции

**Фаза:** P3 · **Слой:** backend, system-design · **Зависит от:** T2.2 · **Размер:** M

## Контекст
В коде есть операции вида «прочитал → решил → записал»:
- `move` страницы: проверил, что новый родитель не потомок, — переместил;
- вставка блока: прочитал позиции соседей — вычислил новую;
- лимиты (позже): посчитал страницы — разрешил создать.

Два таких запроса одновременно могут оба пройти проверку и вместе нарушить инвариант. Пример: A переносит X внутрь Y, B одновременно переносит Y внутрь X — каждый по отдельности валиден, вместе получается цикл, и дерево «отваливается» от корня.

## Цель
Найти все такие места, воспроизвести гонки тестами и защитить инварианты подходящим механизмом.

## Что сделать

### 1. Инструментарий для гонок в тестах
Фикстура, дающая две **независимые** сессии (два соединения) к тестовой БД, и хелпер, запускающий две корутины «одновременно» с точкой синхронизации (`asyncio.Event` / `asyncio.Barrier`), чтобы обе прочитали данные до того, как кто-то запишет. Без барьера гонка воспроизводится случайно.

### 2. Инвентаризация
Таблица в PR: операция → инвариант → чем может быть нарушен → выбранная защита.

### 3. Механизмы (применить там, где уместно)
| Механизм | Когда |
| -------- | ----- |
| Constraint в БД (`UNIQUE`, `CHECK`, FK) | инвариант выражается на уровне строки / пары колонок: `UNIQUE (page_id, position)` у блоков |
| Атомарный `UPDATE ... WHERE` | изменение одной строки с условием (T3.1) |
| `SELECT ... FOR UPDATE` | нужно заблокировать конкретные строки перед проверкой: оба участника `move` |
| `pg_advisory_xact_lock(hash)` | блокировка «понятия», а не строки: «дерево пользователя X меняется» |
| `SERIALIZABLE` + retry | сложная проверка по многим строкам, где проще поручить БД обнаружить конфликт |

Для `move`: блокировать перемещаемую страницу и всю цепочку предков нового родителя в **стабильном порядке** (по id), чтобы не получить deadlock. Или advisory lock на дерево владельца — проще, но сериализует все `move` пользователя. Выбор — в ADR.

### 4. Ретраи
Декоратор / контекстный менеджер `with_retry_on_serialization_failure(max_attempts=3)`: ловит `SerializationFailure` (SQLSTATE `40001`) и `DeadlockDetected` (`40P01`), повторяет **всю транзакцию** с backoff. Не ретраить остальные ошибки.

### 5. Наблюдаемость
Логировать ретраи и deadlock-и с `request_id` (T0.5) — по ним видно, где реальная конкуренция.

## Python-фокус
- `asyncio.Barrier` / `asyncio.Event` для детерминированного воспроизведения гонок.
- Декоратор для async-функции с ретраями; почему ретраить можно только целую транзакцию, а не один запрос.

## Критерии приёмки
- [ ] Тест «перекрёстный move» без защиты падает (цикл в дереве), с защитой — один из запросов 409
- [ ] Тест параллельной вставки двух блоков в одно место — оба вставлены, порядок детерминирован, `UNIQUE` не нарушен
- [ ] Ретраи на `40001` / `40P01` покрыты тестом
- [ ] Таблица инвентаризации и ADR в PR
